# Беспроводной адаптер для Logitech G920 (ESP32-S3) — брифинг проекта

> Контекст для ИИ-ассистента, ведущего разработку.
> **Ревизия 3** — после получения официальной документации GIP от Microsoft.
> Первоисточники лежат в `docs/gip-official/` (docx + извлечённый текст).

## Цель

Беспроводная передача данных между рулём **Logitech G920** и целевой
платформой на базе двух модулей **ESP32-S3**:

- **Передатчик** (у руля): **USB Host**, читает G920.
- **Приёмник** (у платформы): **USB Device**, эмулирует руль.
- Радиоканал: **ESP-NOW v2**.
- **Force Feedback обязателен** — канал двунаправленный.
- **Две цели: Xbox и ПК**, переключаемые. См. раздел «Двухцелевой режим».

## Что случилось в ревизии 3

Через `aka.ms/gipdocs` найден официальный пакет документации Microsoft
(`GIPDocumentation.zip`, 3.4 МБ, 10 документов). MS-GIPUSB на Microsoft Learn
ссылается на него за wire traces, но сам пакет нигде не индексируется.

Внутри, помимо полной спеки GIP, лежит **`H001861 3rd Party USB
Force-Feedback Wheel Specification`** — официальная спецификация протокола
руля с обратной связью для Xbox, включая побайтовые форматы всех сообщений.
Плюс **`H001443 Equation Language for Nextgen Force Feedback Devices`** —
спецификация языка, на котором Xbox описывает силы для руля.

**Следствие: этап 0 (сниффинг) сжимается с «выяснить всё» до «подтвердить
несколько частностей». Формат FFB перестал быть проприетарным чёрным ящиком.**

## Протокол GIP — подтверждённая конкретика

### Дескрипторы USB

```
Interface #0 (Data) — обязателен для всех GIP-устройств:
  bInterfaceClass    0xFF   (Vendor Specific)
  bInterfaceSubClass 0x47   (GIP Subclass)
  bInterfaceProtocol 0xD0   (GIP Protocol)
  bNumEndpoints      0x02
  EP IN  : Interrupt, wMaxPacketSize 64, bInterval ≥ 4
  EP OUT : Interrupt, wMaxPacketSize 64, bInterval ≥ 4
  Polling: до 4 мс / 250 Гц

Interface #1 (Audio) — только если устройство заявляет больше одного
  интерфейса. Изохронные EP: IN 64 байта, OUT 228 байт, bInterval 1.
```

Руль аудио не обязан иметь. Заявлять его не будем — уточнить по сниффу,
объявляет ли его сам G920.

> ⚠️ В старом наброске `~/Documents/g920_usb_dongle/` стояло
> subclass/protocol `0xFF/0xFF` — неверно, должно быть `0x47/0xD0`.

### Заголовок сообщения

4 байта для одиночного пакета, 6+ для фрагментированного (поле TLO —
Total Length or Offset). Длины кодируются с расширением: бит 7 означает
«следующий байт содержит следующие 7 старших бит», до 4 байт.

**Downstream-заголовки обязаны иметь чётный размер** — при необходимости
дополняются через расширение поля длины. Для upstream рекомендуется то же.

Флаги: Fragment, InitFrag, System, **ACME** (ACknowledge ME).

### Тайминги — теперь известны точно

| Событие | Значение |
|---|---|
| Hello в состоянии Arrival | каждые **500 мс**, пока хост не ответит |
| Запрос метаданных хостом | до **4 раз с интервалом 500 мс**, затем устройство помечается на удаление |
| Ответ на метаданные | устройство должно уложиться в **< 500 мс** |
| Status Device (keepalive) | первые 10 с — **каждую секунду**, дальше — **каждые 20 с** |
| ACK timeout на хосте | **100 мс** |
| Запрос ACME устройством (GIP lib ≥ 3.2) | каждые **60 мс** от старта передачи / последнего ACK |
| Reliable message timeout | обычно **1000 мс** |
| Интервал обработки на хосте | **8 мс** |
| Ожидание перед power off/reset | **500 мс** |
| Ответ на extended command | **300 мс** |

**Вывод для радиоканала:** самый жёсткий бюджет — 60–100 мс (ACK/ACME).
ESP-NOW с 1–2 мс в одну сторону укладывается с запасом более чем 30×.
Keepalive-трафик (раз в секунду, потом раз в 20 с) вообще нечувствителен
к задержкам — его даже необязательно держать локально, хотя проще держать.

### Ключевые сообщения

| ID | Название | Направление |
|---|---|---|
| `0x01` | Protocol Control (ACK, фрагментация) | IN/OUT |
| `0x02` | Hello Device | IN |
| `0x03` | Status Device | IN |
| `0x04` | Metadata | IN/OUT |
| `0x05` | Set Device State | OUT |
| `0x06` | **Security** | IN/OUT |
| `0x07` | Guide Button | IN |
| `0x0A` | Wheel Request / Set LED | OUT |

Hello содержит Device ID (8 байт, генерится из PUID крипточипа), VID, PID,
версии прошивки/железа, а также версии RF-, Security- и GIP-протоколов
(все `01.00`).

## Аутентификация

### Что известно

- Сообщение `0x06`, три подтипа: **Security Data** (данные или PUID),
  **Security Data Complete** (флаги `0xA0`, завершает TCP-подобный тройной
  handshake многопакетной передачи), **Security Control** (флаги `0x20`,
  тип `0x02`, сообщает состояние).
- Фрагментированные security-сообщения идут с ACME и Protocol Control ACK.
- В аннотированном трейсе из H001419 объёмы **скромные**: запрос host→device
  14 байт, ответ device→host 90 байт двумя фрагментами (58 + 32).
- Алгоритм реализован в открытом виде в `medusalix/xone`, каталог `auth/`,
  причём **со стороны хоста** — то есть это буквально то, что делает консоль
  (v1 RSA, v2 ECDH, PRF на HMAC-SHA256, транскрипт SHA-256).

### Опт-аут — только для Windows PC

В спеке есть GUID `7a34ce77-7de2-45c6-8ca4-0042c08bd94a`: добавив его в
`SupportedInterfaces` метаданных, устройство отказывается от security-обмена
и **хост засчитывает его успешным по умолчанию**. Формулировка спеки —
«controllers talking to a Windows PC». **На консоли это работать не должно**,
и рассчитывать на это нельзя. Но проверить копейки стоит: если сработает,
passthrough не нужен вообще. Первый эксперимент этапа 1.

### Основной путь — passthrough

Секрет в крипточипе внутри руля, подделать нельзя. Ретранслируем `0x06`
вербатим, крипту понимать не требуется. Что подтверждает реалистичность:

- **GP2040-CE** — работающая open-source прошивка с той же архитектурой
  (`src/drivers/xbone/`): троттлинг ретранслятора **15 мс**, `sleep_ms(50)`
  на старте — и аутентификация проходит.
- Консоль аутентифицирует **один раз при подключении**; при провале
  устройство отваливается примерно через 8 минут.
- GP2040-CE после чужой auth шлёт **свои** input-отчёты, и они принимаются
  → поток данных не привязан к session key.

## Force Feedback — больше не чёрный ящик

**Отменяется прежний тезис «FFB у Logitech проприетарный».** На Xbox руль
не принимает «команды Logitech» — он исполняет **байткод стандартного
языка уравнений Microsoft**. Это спека `H001443`.

### Модель исполнения

- В устройстве **16 уравнений** из общего пула памяти («equation-set»).
- Устройство крутит **equation-set loop**; одна итерация **не быстрее 1 мс**.
- Значения: IEEE-754 float32 и uint32. Оси нормированы в −1.0…1.0
  (педали 0.0…1.0), выход на мотор −1.0…1.0.
- Регистры: скретч `L0..L7`, `E0..E3`, аккумуляторы времени (шаг 100 мкс),
  счётчики прогонов, оси, кнопки как псевдо-ось (битовая маска).
- Состояния уравнения: Unset / Running / Stopped / Paused / Faulted.
- Опкоды (из примеров и Appendix A): `MOV ADD SUB MUL DIV NAND POS GTE LTE
  ABS SIN COS RND END ENDZ`, скипы `SKP/SKPZ/SPN`, битовая логика
  `BAND/BOR/BXOR/BTST/BSET/BCLR`, массивы `ARR/ARRM`, конверсии
  `TOFL/TODW/DIFF_FL/DIFF_DW/MOD_FL/MOD_DW`.

В спеке есть полный разобранный пример: исходник из 17 инструкций →
66 байт ассемблированного кода → два USB-трансфера по 56 байт с точными
байтами. Этого достаточно, чтобы написать ассемблер и дизассемблер.

### Сообщения FFB

| ID | Назначение | Payload |
|---|---|---|
| `0x0B` | Set Application Memory — 10 пар (адрес 2 Б + значение 4 Б) | 0x3C |
| `0x0C` | Set Equation States — по нибблу на каждое из 16 уравнений + Loop State | 0x09 |
| `0x0D` | Set Equation — индекс, размер, смещение, 48 байт кода | 0x35 |

Состояния уравнения: `0x0` Unset, `0x1` Start, `0x2` Stop, `0x3` Pause,
`0x4` Continue, `0xF` Ignore. Loop State: `0x00` Normal, `0x01` Pause,
`0x02` Forces Off.

Важно: **фрагментация GIP для 0x0D не используется** — приёмный буфер
устройства никогда не должен превышать 64 байта. Длинное уравнение шлётся
несколькими запросами со смещением.

## Формат данных руля

### Wheel State Report (0x20), 17 байт

```
0x00  0x20            идентификатор
0x01  Flags = 0x00
0x02  Sequence ID     инкремент
0x03  Length ≥ 0x11
0x04  [7..2] Y X B A View Menu, [1..0] reserved
0x05  Right/Left Paddle, DPAD R/L/D/U
0x06  Wheel Rotation Angle    (2 байта, LE)
0x08  Throttle                (2 байта)
0x0A  Brake                   (2 байта)
0x0C  Clutch                  (2 байта)
0x0E  Hand Brake              (1 байт)
0x0F  H-Shifter Type (3 бита) + Max Gear
0x10  H-Shifter Value  (0 нейтраль, 0xFF реверс)
0x11  Angle Setting           (2 байта, градусы)
0x13  Power Level             (0..255)
0x14  биты подключения педалей + Has Power
```

Все значения — **unsigned little-endian**. Разрядность каждой оси задаётся
не здесь, а в конфигурационном отчёте: `0` = крайнее против часовой,
`2ⁿ⁻¹` = центр, `2ⁿ−1` = крайнее по часовой.

### Wheel Static Configuration Report (0x21), ≥ 11 байт

Отдаётся в ответ на Initial Reports Request. Содержит разрядность каждой
оси (Angle/Throttle/Brake/Clutch/Handbrake; `0` = ось отсутствует),
Min/Max Angle Setting, **Force-Feedback Axis mask** (бит 0 — руль, 1 — газ,
2 — тормоз, 3 — сцепление, 4 — ручник, 5 — низкочастотный мотор,
6 — высокочастотный), флаги Hard/Soft Angle Change, H-Shifter, тип вибро.
Payload > 0x0B означает наличие vendor-специфичного хвоста.

### Wheel Requests (0x0A), payload всегда 0x03

`0x00` Initial Reports, `0x01` Angle Change (угол в градусах),
`0x02` Power Level (0..255, линейно по ощущению), `0x03` Vibration Motor.

## Архитектурное следствие

Раз протокол руля стандартизован, приёмнику **не нужно копировать G920
побайтово** — достаточно реализовать корректное GIP-устройство класса
«руль» по H001861, объявив VID/PID реального руля (`046D:C261`), чтобы
security-ответы настоящего чипа не расходились с заявленной личностью.

G920 — лицензированный руль Xbox, то есть он **обязан** соответствовать
H001861. Значит его поведение предсказуемо с высокой точностью, и снифф
нужен для проверки, а не для реверса.

## Радиоканал

Auth-сообщения по трейсу небольшие (десятки байт), но метаданные и
сертификаты могут превышать 250 байт. **ESP-NOW v2** (ESP-IDF ≥ 5.4)
поднимает лимит до ~1450 байт — своя фрагментация не нужна.

→ **ESP-IDF ≥ 5.4, ESP-NOW v2.**

## Режимы G920

Отдельной «PC-версии» не существует (PS-аналог — G29). Один руль:

| Режим | PID | Класс | Протокол |
|---|---|---|---|
| **Xbox** (по умолчанию при включении) | `046d:c261` | vendor `0xFF` | GIP |
| PC (после vendor-команды от драйвера) | `046d:c262` | HID `0x03` | HID++ |

Переключает драйвер Windows; в базе `usb_modeswitch` фигурирует
`0f 00 01 01 42`. Передатчику достаточно **не переключать** руль.

## Двухцелевой режим: ПК и Xbox

Требование — один адаптер, работающий и с консолью, и с ПК.

### Ключевая асимметрия

| | Xbox | ПК (Windows) |
|---|---|---|
| Режим руля | `c261`, GIP | `c262`, HID / HID++ |
| Аутентификация | **обязательна**, passthrough | **отсутствует** |
| FFB | байткод уравнений (`0x0B/0x0C/0x0D`) | HID++ feature `0x8123` |
| Опрос USB | ≥ 4 мс (250 Гц) — свободно | обычно 1 мс (1000 Гц) — **туго** |
| Сложность протокола | высокая | низкая |
| Сложность таймингов | низкая | **высокая** |

Асимметрия перевёрнутая: Xbox сложнее по протоколу, ПК — по таймингам.
ПК-путь не «упрощённая версия» Xbox-пути, а другой набор проблем.
Зато ПК-путь можно довести до рабочего состояния **первым**: там нет auth,
то есть нет самого рискованного звена.

### Архитектура: зеркалирование, а не нормализация

Рассматривались два подхода.

**Нормализация** — держать руль всегда в одном режиме, гонять по радио свой
универсальный формат, а приёмник рендерит его в GIP или HID. Отвергнуто:
FFB-модели несовместимы концептуально. Xbox — байткод-машина с 16
уравнениями, исполняемая в устройстве; HID++ — набор эффектов с
параметрами. Транслировать эффекты в байткод теоретически можно (язык это
позволяет: `SIN`, `MUL`, оси-регистры), но это отдельный компилятор с
собственным классом багов, и он нужен только чтобы не делать переключение
режима — которое делается одной vendor-командой.

**Зеркалирование (выбрано).** Передатчик держит руль в том режиме, который
соответствует цели; приёмник предъявляет соответствующую личность; трафик
туннелируется **вербатим** в обе стороны. Два профиля туннеля,
общий транспорт. Никакой трансляции FFB — ни в одну сторону.

```
        ┌── Xbox-профиль ──┐                  ┌── Xbox: GIP c261 ──┐
G920 ───┤                  ├─ ESP-NOW v2 ─────┤                    ├─── цель
        └── PC-профиль ────┘                  └── PC: HID c262 ────┘
```

### Клонирование личности вместо хардкода

Важный принцип: **не зашивать дескрипторы в прошивку приёмника.**
Передатчик при подключении руля вычитывает с него всё, что определяет
личность, и передаёт приёмнику, тот кэширует в NVS и предъявляет хосту:

- device/config/interface/endpoint дескрипторы, строковые дескрипторы;
- в PC-режиме — HID report descriptor;
- в Xbox-режиме — **блоб метаданных GIP** (сообщение `0x04`) и содержимое
  Hello (`0x02`) с Device ID, версиями прошивки и железа.

Это критично именно для Xbox: консоль кэширует метаданные по связке
VID/PID/Revision, а Device ID генерится из PUID крипточипа. Своя,
написанная от руки метадата рискует разойтись с тем, за что ручается
security-обмен. Ретранслируем настоящее — расхождений нет по построению.

Побочная выгода: адаптер становится не «эмулятором G920», а зеркалом
конкретного подключённого руля. G923 или Thrustmaster заработают без
правок прошивки (при условии, что они тоже следуют H001861).

### Переключение режима руля

**Решение по эксплуатации: определение статично на сессию.** Хост
опознаётся один раз при подключении USB, режим фиксируется до конца сессии.
Смена платформы = переподключение USB. Это снимает необходимость менять
режим руля на лету и вопрос с возвратом `c262 → c261` программно: после
передёргивания руль сам поднимается в `c261`.

- **Xbox → нужен `c261`:** состояние по умолчанию при включении, ничего не
  делаем.
- **ПК → нужен `c262`:** передатчик шлёт рулю vendor-команду, руль
  отцепляется и переподключается как HID-устройство.

#### Команда переключения — подтверждена

Байты `0F 00 01 01 42`, отправляются **на interrupt OUT endpoint 0x01**
(не control transfer). Именно это делает `usb_modeswitch` на Linux:

```
DefaultVendor=046d    DefaultProduct=c261
TargetVendor=046d     TargetProduct=c262
MessageEndpoint=01    ResponseEndpoint=01
MessageContent="0f00010142"
NoDriverLoading=1
```

Разбирается как обычное GIP-сообщение с 4-байтовым заголовком:

| Байт | Значение | Поле GIP |
|---|---|---|
| `0F` | команда | vendor-specific (в спеке H001419 не определена) |
| `00` | флаги | не фрагмент, ACK не требуется |
| `01` | sequence | |
| `01` | payload length | 1 байт |
| `42` | payload | «переключись в HID» |

То есть для передатчика это не особый случай, а рядовая отправка
GIP-сообщения в тот же endpoint, куда идёт весь остальной downstream-трафик.

**Команда не G920-специфична.** Ровно та же последовательность переключает
Logitech G923 Xbox (`c26d` → `c26e`) — подтверждено в issue драйвера G923.
Значит это общий вендорский механизм Logitech для рулей в Xbox-режиме, и
адаптер заработает с G923 без правок.

#### Поправка: ядро Linux этого не делает

Встречается утверждение, что переключение выполняет драйвер `xpad`.
Проверено по актуальному `drivers/input/joystick/xpad.c` — **записи для
`046d:c261` там нет**. Патч Саймона Вуда 2015 года (`INPUT: xpad: Add
minimal support for Logitech G920 Wheel`) в ядро не вошёл; из той серии
приняли только HID++-часть. Переключение сегодня делает userspace —
`usb_modeswitch` по udev-правилу. Для нас это выгодно: механизм полностью
в нашей власти, ничего не конфликтует.

### Автоопределение хоста

Требование: протокол выбирается **только по хосту**, без переключателей и
настроек. Это выполнимо. Ключ — в том, что личность не обязана быть
окончательной с первой энумерации: USB-устройство вправе отцепиться и
переподключиться другим. Именно так ведёт себя сам G920 (`c261` → `c262`),
так что приём штатный, а не трюк.

**Схема: подняться как GIP → опознать хост → при необходимости
переэнумерироваться как HID.**

GIP выбран стартовой личностью не случайно: он работает **на обеих**
платформах (в Windows 10+ драйвер GIP встроенный, устройство появляется в
разделе «Xbox Peripherals»). То есть неверно угаданный «Xbox» на ПК всё
равно даёт рабочий руль — просто без G HUB. Обратная ошибка фатальна:
HID-устройство на консоли не опознаётся вообще.

> **Асимметрия цены ошибки задаёт смещение детектора: по умолчанию GIP,
> уход в HID — только по положительному подтверждению, что хост это ПК.**

#### Различать надо не ОС, а «консоль или не консоль»

Принципиальное упрощение: детектору **не нужно знать операционную систему**.
Как только вердикт «не Xbox» — приёмник поднимается клоном `c262`, и дальше
всё делают штатные драйверы: `hid-logitech-hidpp` в ядре Linux (G920
поддержан с 6.3, FFB через HID++ `0x8123`), он же на SteamOS/Steam Deck,
G HUB на Windows, HID-стек на macOS. **ПК-ветка не требует ни строчки кода
под конкретную ОС.**

Значит задача сводится к бинарному вопросу: *это игровая консоль Xbox или
что угодно другое?* И это удобно, потому что Xbox — **один** фиксированный
детерминированный хост, а «всё остальное» опознавать по отдельности не надо.

→ **Опознаём Xbox положительно. Всё, что не опознано как Xbox, — ПК.**

Это переворот относительно предыдущей редакции: строить детектор на
Windows-признаках (`device_qualifier`, строка `0xEE`, MS OS Descriptor)
нельзя — Linux, SteamOS и macOS их не запрашивают и были бы приняты за
консоль. Эти признаки остаются, но только как вспомогательные.

#### Решающее дерево на уровне GIP

Ключ в том, что вендорский класс `0xFF/0x47/0xD0` на обычном ПК **никем не
обслуживается**. Linux без `xone`, SteamOS, macOS не имеют драйвера GIP —
они завершат USB-энумерацию и замолчат навсегда. Windows 10+ драйвер GIP
имеет и ответит, но security-обмен не проводит. Только консоль делает и то,
и другое.

```
Поднялись как GIP, шлём Hello каждые 500 мс.

A. Тишина > 2 с (никто не ответил на Hello)
   → хост не понимает GIP → ПК   (Linux, SteamOS, macOS, Windows без драйвера)

B. Ответил (Metadata Request / Set Device State), затем пришёл 0x06 Security
   → Xbox

C. Ответил, дошёл до START, security нет 1 с
   → ПК   (Windows со встроенным GIP-драйвером)
```

Три ветки покрывают все платформы, и ни одна не опирается на особенности
конкретной ОС. Пороги опираются на спеку: устройство шлёт Hello каждые
500 мс, хост запрашивает метаданные до 4 раз с интервалом 500 мс — то есть
живой GIP-хост проявляется в пределах ~500 мс, и 2 с тишины означают, что
его нет.

Для ветки C в метаданные вписывается опт-аут GUID
`7a34ce77-7de2-45c6-8ca4-0042c08bd94a`: по спеке хост-ПК с ним «засчитывает
security-обмен успешным по умолчанию». Консоль опт-аут, названный в спеке
Windows-специфичным, игнорировать обязана.

#### Смещение и цена ошибки

По умолчанию до вынесения вердикта — GIP, потому что цена ошибок разная.
Ошибочный «Xbox» на ПК даёт рабочий, хоть и менее интегрированный руль
(в Windows GIP-устройство встаёт как «Xbox Peripherals»; на Linux — ничего,
но это чинится повторным опознанием). Ошибочный «ПК» на консоли даёт
мёртвое железо: HID-устройство Xbox не опознаёт вообще.

> **Появление `0x06` в любой момент немедленно отменяет вердикт «ПК» и
> возвращает GIP.** Это единственный сигнал с правом вето.

#### Вспомогательные сигналы (ускоряют, но не решают)

Нужны, чтобы не ждать 2 с там, где всё ясно раньше:

- **Запрос `device_qualifier`** — спека велит отвечать STALL, иначе Windows
  покажет «This device can perform faster». Виндовизм; консоли не нужен.
- **Строка `0xEE` / `MSFT100`, Extended Compatible ID (`XGIP10`),
  Extended Properties** — запрашивает Windows. Оговорка: Windows кэширует
  это по `[VID][PID][bcdDevice]` и при повторном подключении знакомого
  устройства запросы не повторяет, так что отсутствие признака ничего не
  доказывает.
- **Фингерпринт энумерации** — порядок и повторность `GET_DESCRIPTOR`,
  набор строковых индексов, языковые ID, интервалы между `SET_ADDRESS` и
  `SET_CONFIGURATION`. Стеки Xbox, Windows, Linux и SteamOS различаются
  измеримо, и это не кэшируется.

Любой из них при подтверждении «это Windows/Linux» позволяет вынести вердикт
ПК досрочно, не дожидаясь полного окна тишины. Но **ни один не имеет права
перевести в HID при наличии security-трафика.**

#### Известный проблемный случай: Linux с установленным `xone`

`xone` привязывается к интерфейсу `0xFF/0x47/0xD0` и реализует
auth-handshake **со стороны хоста**. То есть Linux-машина с установленным
`xone` ответит на Hello и пришлёт `0x06` — и по дереву выше будет опознана
как Xbox. Руль останется в GIP-режиме, а поскольку `xone` рули не
поддерживает (в README чекбокс не отмечен), работать он не будет.

Случай узкий — требует, чтобы пользователь осознанно поставил `xone`, —
но реальный. Разрешается фингерпринтом энумерации (стек Linux ≠ стек
консоли) и, в крайнем случае, ручным оверрайдом. В логике детектора это
единственное место, где нужен признак уровня USB, а не GIP.

#### Что уже подтверждено практикой чужими проектами

Верность выбранной схемы «туннелировать USB вербатим, а не транслировать»
подтверждается тем, что она работает у других на куда худшем транспорте:

- **VirtualHere / USB Network Gate / USB-over-IP** прокидывают рули с
  работающим FFB по TCP через сеть. Сообщаемая задержка на проводном
  соединении — около 1 мс. Это доказывает, что руль не имеет скрытых
  требований к USB-таймингам, которые ломались бы при туннелировании: важна
  только задержка, а она у ESP-NOW того же порядка.
- **`jocover/esp32s3_xbox_adapter`** — адаптер контроллеров Xbox на
  ESP32-S3: рабочий пример связки USB-OTG + радио на нашем железе.
- **`GP2040-CE`** — GIP-эмуляция и auth-passthrough на RP2040.

Ни один из них не делает трансляцию форматов — все гоняют байты as-is.

#### Последовательность при вердикте «ПК»

1. Приёмник сообщает передатчику: нужен PC-режим.
2. Передатчик шлёт рулю `0f 00 01 01 42`, руль переподключается как `c262`.
3. Передатчик снимает HID report descriptor и отдаёт приёмнику.
4. Приёмник отцепляется от USB и поднимается заново как клон `c262`.

Суммарно 2–4 с от втыкания до готовности. Для сравнения: сам G920 на
Windows делает ровно то же самое.

При вердикте «Xbox» ничего не происходит — руль уже в `c261`, приёмник уже
GIP, обмен продолжается без разрыва. Важно, что детектирование **пассивное**:
мы ничего не задерживаем и ни на что не отвечаем медленнее, поэтому окно
опознания не крадёт время у auth-фазы.

#### Жизненный цикл вердикта: питание против bus reset

Их надо различать, иначе донгл будет перезапускать опознание на каждый
чих.

| Событие | Что видит донгл | Что делаем |
|---|---|---|
| Выдернули кабель | пропал VBUS, MCU обесточен | новая сессия, детект заново |
| Перезагрузка хоста | **bus reset без потери питания** | личность сохраняем |
| Suspend / resume | bus reset или suspend | личность сохраняем |
| Перезагрузка драйвера ОС | переэнумерация | личность сохраняем |

Ключевой факт: **при тёплой перезагрузке ПК VBUS обычно не пропадает** —
многие машины держат питание на портах и при ребуте, и в S5. Донгл
переживает перезагрузку хоста, не сбрасываясь; он видит только
переэнумерацию. Если привязать детект к bus reset, устройство будет уходить
в двухсекундную GIP-фазу после каждого выхода из сна.

→ **Конструктивное требование: приёмник питается от шины.** Тогда
«выдернули» однозначно означает чистое состояние, и не нужно гадать, жив
ли ещё MCU.

Смена ОС на том же железе (Windows ↔ Linux в дуалбуте) вердикт **не меняет
вообще**: детектор различает консоль и не-консоль, обе ОС — «ПК», личность
одна и та же. Донгл этого события просто не заметит.

#### Самокоррекция: вердикт проверяемый, а не окончательный

Опасный случай — **медленный хост**. Донгл воткнут в выключенный Xbox,
консоль включают: VBUS появился, донгл шлёт Hello, а GIP-стек консоли ещё
не поднялся. Если молчание длится дольше порога, выносится «ПК», донгл
уходит в HID — и консоль получает мёртвое устройство. Симметрично на ПК:
между энумерацией в BIOS и загрузкой драйвера ОС легко проходят секунды.

Подбором порога это не лечится: порог, достаточный для медленного хоста,
делает старт неприятно долгим для быстрого. Лечится тем, что **любой
вердикт можно опровергнуть и откатить**:

```
GIP-режим:  нет ответа на Hello и нет 0x06 за T1   → пробуем HID
HID-режим:  SET_CONFIGURATION прошёл, но хост не опрашивает
            наш interrupt IN endpoint дольше T2     → откат в GIP
любой:      пришёл 0x06                             → GIP, фиксация
```

Второе правило — ключевое и почти бесплатное: любой ПК, подобравший
HID-устройство, начинает дёргать IN endpoint сразу по своему `bInterval`.
Xbox нераспознанное HID-устройство просто игнорирует. Признак «энумерация
прошла, а IN-токенов нет» однозначно означает неверно угаданную личность —
и не зависит от того, насколько медленно грузился хост.

Итог: донгл колеблется между двумя личностями, пока одна не приживётся.
Медленный хост стоит одного лишнего цикла, а не сломанной работы.
T1 и T2 калибруются на этапе 1b, стартовые прикидки — 2 с и 3 с.

#### Кэш вердикта

Результат сохраняется в NVS и применяется сразу при следующем подключении —
тогда ПК получает готовое HID-устройство без промежуточной GIP-фазы.
При расхождении (ожидали ПК, а пришёл `0x06`) — откат в GIP и
переэнумерация. Типовой сценарий «всегда одна и та же платформа» становится
мгновенным, смена платформы — на пару секунд дольше.

#### Что остаётся ручным

Ничего в обычной работе. Смена платформы — переподключение USB, вердикт
выносится заново. Аварийный выход — принудительная фиксация режима долгим
удержанием кнопки, на случай хоста, которого мы не предвидели
(например, Linux с установленным `xone`).

#### Что даёт ПК-ветка без единой строчки под ОС

После вердикта «ПК» приёмник — клон `c262`, и дальше работают штатные
драйверы:

| Платформа | Драйвер | FFB |
|---|---|---|
| Linux ≥ 6.3 / SteamOS / Steam Deck | `hid-logitech-hidpp` (`HIDPP_QUIRK_CLASS_G920`) | HID++ `0x8123` |
| Windows | G HUB / встроенный HID | HID++ `0x8123` |
| macOS | HID-стек | базовый |

Всё поведение FFB реализовано в прошивке самого руля — мы только
ретранслируем HID++-обмен. Ни `new-lg4ff`, ни `lg4ff_userspace` тут ни при
чём: оба явно не поддерживают G920, он обслуживается штатным HID++-драйвером.

### Тайминги: ПК — узкое место

Xbox по GIP опрашивает не чаще 250 Гц, а самый жёсткий срок — 60–100 мс
(ACME/ACK). Запас над ESP-NOW тридцатикратный.

ПК-режим тяжелее: HID обычно 1 мс, и игры шлют FFB плотным потоком.
Радио с 1–2 мс в одну сторону становится сопоставимо с периодом опроса.
Меры, которые нужно заложить в транспорт сразу:

- **Коалесценция FFB.** Гнать не каждый пакет, а последнее состояние на
  момент отправки — FFB идемпотентен по смыслу, промежуточные значения
  устаревают. Целевая частота вниз — 200–500 Гц.
- **Разделение приоритетов.** Ось руля важнее педалей, состояние важнее
  истории. Терять промежуточные отчёты допустимо, финальный — нет
  (иначе «залипшие» органы управления — H001861 прямо об этом
  предупреждает для Xbox, и на ПК верно то же).
- **Отдельный фиксированный такт на приёмнике.** Приёмник отдаёт хосту
  отчёты по своему таймеру из последнего полученного состояния, а не по
  факту прихода радиокадра. Джиттер радио не должен протекать в USB.
- Фиксированный Wi-Fi канал, отключённое энергосбережение, `esp_wifi_set_ps(WIFI_PS_NONE)`.

### Общий транспорт

Один слой на оба профиля: тип кадра (INPUT / FFB / AUTH / CONTROL /
DESCRIPTOR), счётчик последовательности, флаг «требуется доставка».
AUTH и DESCRIPTOR — надёжные, с подтверждением и ретраями. INPUT и FFB —
ненадёжные, свежесть важнее полноты. ESP-NOW v2 (≈1450 байт) покрывает
любое GIP-сообщение и любой дескриптор одним кадром.

## План разработки

Детальный роадмап с вехами, критериями готовности и зависимостями вынесен в
**[`docs/ROADMAP.md`](docs/ROADMAP.md)** — там же структура репозитория и
разделение на две прошивки (TX у руля / RX-донгл у хоста).

Кратко, порядок и его логика:

| Веха | Суть |
|---|---|
| M0 | Каркас: два проекта ESP-IDF, общие компоненты, логи |
| M1 | **TX: USB Host** — руль оживает, снимается весь снифф |
| M2 | **RX: GIP-заглушка** — эталоны хостов, тайминги T1/T2 |
| M3 | Транспорт ESP-NOW v2, замер задержек и потерь |
| M4 | Клонирование личности руля вместо зашитых дескрипторов |
| M5 | **ПК-ветка end-to-end — первый работающий продукт** |
| M6 | Детектор хоста с самокоррекцией |
| M7 | Xbox: GIP без аутентификации |
| M8 | **Auth passthrough — работающий продукт для Xbox** |
| M9 | FFB на Xbox |
| M10 | Надёжность, мёртвая рука, индикация |

Две вещи задают этот порядок. Первая: **M1 и M2 независимы** и идут
параллельно — M2 даёт эталоны для детектора задолго до того, как детектор
понадобится. Вторая: **ПК-ветка идёт раньше Xbox**, потому что в ней нет
аутентификации (нет самого рискованного звена), а тайминги при этом самые
жёсткие — обкатать их лучше там, где больше ничего не мешает.
Самое рискованное, auth passthrough, стоит поздно, когда всё остальное уже
работает.

## Остаточные риски

- **Политика Microsoft.** С ноября 2023 консоль блокирует неавторизованные
  аксессуары (ошибка `0x82d60002`); прошивки могут ужесточать проверки.
- **Тайминги ПК-ветки.** HID на 1 мс против ESP-NOW на 1–2 мс в одну
  сторону — запас минимальный. Коалесценция обязательна, но насколько
  просядет ощущение FFB — покажет только тест.
- **Возврат руля в Xbox-режим.** Если сброс VBUS не помогает, смена цели
  потребует передёргивания кабеля. Для автоопределения это критичнее, чем
  для ручного выбора: детектор рассчитывает на то, что режим меняется
  программно.
- **Детектор хоста.** Реакция консоли на security-опт-аут GUID не проверена.
  Linux с установленным `xone` отвечает на GIP и шлёт `0x06`, то есть
  выглядит как консоль, — разрешается только фингерпринтом энумерации.
  Смещение в сторону GIP делает ошибку нефатальной, но пороги требуют
  эталонов со всех платформ (этап 1b).
- **Медленный хост при холодном старте.** Закрыто самокоррекцией, но цена —
  до пары лишних переэнумераций на старте. Если T1/T2 окажутся большими,
  время до готовности вырастет, и это будет заметно пользователю.
- **Тайминги USB Host на передатчике.** ESP32-S3 должен успевать за
  bInterval руля; запас есть, но не измерен.
- **Аудио-интерфейс.** Если G920 его объявляет и консоль этого ждёт —
  придётся эмулировать изохронные endpoint'ы, это заметно сложнее.
