# Roadmap разработки прошивок

> Две независимые прошивки с общим ядром. Контекст, протоколы и обоснование
> решений — в [`../wireless-g920-project.md`](../wireless-g920-project.md).
> Первоисточники Microsoft — в [`gip-official/`](gip-official/).

## Две ветки

| | **TX** — передатчик | **RX** — донгл |
|---|---|---|
| Где стоит | у руля | у хоста (ПК/Xbox) |
| Роль USB | **Host** | **Device** |
| Стек | ESP-IDF USB Host Library | TinyUSB **голый**, не `esp_tinyusb` |
| Питание | от своего источника | **от шины USB** (обязательно) |
| Главная задача | читать руль, переключать его режим | притворяться рулём, опознать хост |
| Сложность | средняя, стек капризный | высокая, вся логика личности здесь |

Ветки разные по существу, а не по сборке: у S3 один USB-OTG контроллер, он
либо Host, либо Device. Поменять роль на лету нельзя — отсюда два модуля и
две прошивки.

## Структура репозитория

ESP-IDF, два проекта с общим каталогом компонентов:

```
firmware/
  common/                    # EXTRA_COMPONENT_DIRS для обоих проектов
    link/                    # ESP-NOW v2: пиринг, кадры, надёжная доставка
    proto/                   # типы кадров TX↔RX, версия протокола линка
    gip/                     # GIP: заголовки, фрагментация, сборка сообщений
    identity/                # снятая личность руля, сериализация, NVS
    util/                    # логирование, hexdump, кольцевые буферы
  tx/                        # приложение передатчика
    main/
  rx/                        # приложение донгла
    main/
docs/
  ROADMAP.md
  gip-official/
```

`common/gip` нужен обеим сторонам: TX разбирает поток от руля, RX собирает
и разбирает поток от хоста. Это единственный крупный кусок протокольной
логики, который честно общий.

**Требование к тулчейну: ESP-IDF ≥ 5.4** — ниже нет ESP-NOW v2, а с лимитом
250 байт пришлось бы писать свою фрагментацию поверх уже имеющейся в GIP.

## Порядок вех

M1 и M2 независимы и делаются параллельно — это важно, потому что M2 даёт
эталоны для детектора задолго до того, как понадобится сам детектор.

```
M0 каркас
 ├─ M1 TX: USB Host ──────┐
 └─ M2 RX: GIP-заглушка ──┤
                          ├─ M3 транспорт ── M4 клон личности ─┐
                          │                                     ├─ M5 ПК-ветка ── M6 детектор
                          └─────────────────────────────────────┘        │
                                                                          └─ M7 Xbox GIP ── M8 auth ── M9 FFB ── M10 надёжность
```

---

## M0 — каркас

**Ветка:** обе. **Железо:** 2× ESP32-S3-DevKitC-1.

- Два проекта ESP-IDF, общий `EXTRA_COMPONENT_DIRS`, обе прошивки собираются
  и мигают светодиодом.
- Логирование в UART (не в USB-CDC — USB занят обеими ролями), hexdump,
  единый формат меток времени с микросекундной точностью: он понадобится
  для всех замеров дальше.
- Обёртки NVS, версионирование сохранённых структур.

**Готово когда:** `idf.py build` проходит для обеих, лог с временными
метками идёт в UART на обеих платах.

---

## M1 — TX: USB Host, руль оживает

**Ветка:** TX. **Железо:** TX-плата + G920 + его БП.

- `usb_host_lib` + свой клиент, обработка подключения/отключения.
- Захват vendor-интерфейса `0xFF / 0x47 / 0xD0`, открытие interrupt IN/OUT.
- Непрерывное чтение IN, отправка в OUT.
- **Полный дамп в лог:** device/config/interface/endpoint дескрипторы,
  строковые дескрипторы, весь трафик с метками времени.

**Это и есть этап сниффинга.** Отдельный стенд на Raspberry Pi не нужен:
передатчик видит всё, что руль говорит, и всё, что ему говорят.

Здесь же закрываются оставшиеся неизвестные:

- [ ] объявляет ли G920 аудио-интерфейс #1;
- [ ] блоб метаданных GIP (сообщение `0x04`) целиком;
- [ ] Wheel Static Configuration `0x21`: разрядности осей, FFB axis mask,
      Min/Max угол;
- [ ] версия security-протокола из Hello;
- [ ] реальный `bInterval`;
- [ ] отвечает ли руль на `0F 00 01 01 42` до отцепления.

Отдельная подзадача — **переключение в PC-режим**: отправить команду в
interrupt OUT, дождаться отцепления, переэнумерировать руль как `c262`,
снять HID report descriptor и HID++-обмен.

**Готово когда:** в логе лежат оба режима руля целиком — дескрипторы,
метаданные, init-последовательность, поток отчётов.

**Риск:** капризность USB Host стека на S3 при работе с vendor-классом.
Митигация — начать с примера `usb_host_lib` из ESP-IDF и наращивать.

## M2 — RX: GIP-заглушка и эталоны хостов

**Ветка:** RX. **Железо:** RX-плата + Xbox + ПК/ноут.

- TinyUSB vendor-класс, дескрипторы по MS-GIPUSB: интерфейс #0,
  `0xFF/0x47/0xD0`, два interrupt endpoint по 64 байта, `bInterval` 4.
  **Стек берётся голый (`espressif/tinyusb`), а не обёртка `esp_tinyusb`:**
  обёртка реализует `tud_descriptor_string_cb` сама и на индекс `0xEE`
  отвечает STALL, а это MS OS Descriptor из пункта ниже. В вехе, где
  предмет проверки — что именно спросил хост и что именно получил,
  прослойка, отвечающая за нас, стоит наблюдаемости.
- Device Qualifier → **STALL** (иначе Windows покажет «This device can
  perform faster»).
- MS OS Descriptor: строка `0xEE` = `MSFT100`, vendor code `0x90`,
  Extended Compatible ID = `XGIP10`, Extended Properties → **STALL**.
- Hello (`0x02`) каждые 500 мс до ответа хоста.
- **Логировать всё, что делает хост:** каждый control-запрос, его порядок,
  интервалы, реакцию на Hello, наличие `0x06`, опрос IN endpoint.

Снять эталоны:

- [x] Xbox — эталон «консоль» **снят 02.08.2026, и он опроверг посылку
  этой вехи: по энумерации консоль и Windows категориально неразличимы**
  (общий стек USB — Xbox OS стоит на ядре Windows). Остаются тайминги, но
  надёжный разделитель лежит после Announce, то есть после M4. Разбор в
  [`HOSTS.md`](HOSTS.md)
- [x] Windows — **снят 02.08.2026, и состояний оказалось три, а не два:**
  «устройство совсем новое» (спрашивает `0xEE` и Extended Properties),
  «кэш сброшен, драйвер стоит» (только `0xEE`), «кэш на месте» (ничего).
  Кэш `usbflags` подтверждён реестром: `osvc = 1 144`, где 144 = `0x90`
- [x] Linux чистый, без `xone` — **снят 02.08.2026**
- [x] Linux с `xone` — **снят, и предположение оказалось неверным:** `xone`
  подбирается по белому списку вендоров, Logitech `046d` в нём нет, значит
  перехвата не будет. Проблема обратная — на Linux в GIP-режиме нас не
  подхватит никто. Разбор в [`HOSTS.md`](HOSTS.md)
- [x] macOS — **снят 02.08.2026**: единственный, кто не доходит до
  `SET_CONFIGURATION` вовсе

Замерить **T_enum1** (от появления питания до первого control-запроса
хоста) и **T_enum2** (от **последней** `SET_CONFIGURATION` перед первым
опросом IN до самого опроса).

⚠ **Имена разведены намеренно, по итогам первого захода судьи.** Раньше обе
величины назывались T1 и T2 — теми же буквами, что пороги детектора в M6, —
и «Готово когда» молча предположило, что это одни и те же числа. Это не
так: в M6 `T_silence` означает тишину на уровне **GIP** (нет ответа на
Hello), а `T_hid_idle` — простой IN в **HID**-режиме. M2 поднимает
vendor-класс GIP и меряет энумерацию; ни одну из тех двух величин она
измерить не может, и это свойство порядка вех, а не недоработка.

⚠ **Про «худший случай» — постановка исправлена по результатам замера.**
Здесь стояло «воткнуть в выключенный хост и включить». Для девкита это
осмысленно, для продукта — нет: T-Dongle питается от шины, при выключении
хоста VBUS пропадает и донгл умирает, ждать в тишине ему нечем. Включится
хост — донгл загрузится вместе с ним, а это обычный горячий случай.
Опасна не выключенная консоль, а **живой хост, который молчит**: macOS и
Linux молчат навсегда. Замер и разбор — в [`HOSTS.md`](HOSTS.md).

Здесь же проверить security-опт-аут GUID
`7a34ce77-7de2-45c6-8ca4-0042c08bd94a` на консоли.

⚠ **Отложено до M1.** Брифинг числит это «первым экспериментом этапа 1» и
оценивает в копейки, но GUID вписывается в `SupportedInterfaces` **блоба
метаданных**: эксперимент требует сериализовать метаданные GIP целиком.
Формат описан в `gip-official/txt/GIP Metadata Specification.txt`, так что
дело в объёме, а не в незнании — и тот же модуль нужен в M4 и M7.
Написанный до дампа руля, он почти наверняка разойдётся с тем, что руль
присылает на самом деле.

**Готово когда:** есть таблица «платформа → набор признаков → тайминги
энумерации», и **для каждого порога детектора M6 названо, выводится ли он
из этой таблицы или в какой вехе снимается**.

Формулировка исправлена 02.08.2026 по итогам первого вердикта. Прежняя
звучала «…из которой берутся пороги детектора» и была невыполнима внутри
вехи: два из трёх порогов M6 требуют того, чего у M2 нет по построению —
HID-режима (появляется в M5) и годного Announce, то есть личности руля
(появляется в M4, а заглушке её иметь **запрещает И2**). Правка не смягчает
критерий: обязательство никуда не делось, оно переехало под вехи, которые
физически могут его закрыть, каждая со своим `[J]`-гейтом. Таблица живёт в [`HOSTS.md`](HOSTS.md): все семь состояний сняты
02.08.2026.

**Steam Deck убран из вехи 02.08.2026 решением человека** — вернётся
отдельной строкой, когда железо будет под рукой. Веха его не ждёт: по ядру
SteamOS это тот же стек, что «Linux чистый», а строка «Linux чистый» уже
снята. Ожидание, что они совпадут, — гипотеза, и когда Deck появится, её
надо будет проверить, а не засчитать.

⚠ **Судья дал по этому критерию BLOCK, и по делу.** Таблица даёт признаки
энумерации и её тайминги, но **не даёт порогов детектора**: T1 в ней — «от
VBUS до первого control-запроса USB», а M6 нужна тишина на уровне GIP; T2
снят на vendor-классе GIP, а применяется он к откату из **HID**-режима.
Настоящий T2 снимается в M5, порог GIP-тишины — после M4.

## M3 — транспорт

**Ветка:** common/link. **Железо:** обе платы.

- ESP-NOW v2, фиксированный канал, `esp_wifi_set_ps(WIFI_PS_NONE)`,
  автоматический пиринг с сохранением MAC в NVS.
  **Было «пиринг по кнопке» — переехало в M10** («Пиринг: сброс, повторное
  сопряжение»). В M3 кнопка не нужна: пока комплект один, автоматический
  пиринг находит пира сам, а ручное сопряжение — это про то, как
  *пере*связать модули, то есть про эксплуатацию.
- Кадр: тип, номер, флаги. Типы — `INPUT`, `FFB`, `AUTH`, `CONTROL`,
  `DESCRIPTOR`.
- Две дисциплины доставки:
  - **надёжная** (`AUTH`, `DESCRIPTOR`, `CONTROL`) — подтверждение, ретраи;
  - **свежая** (`INPUT`, `FFB`) — без ретраев, новое вытесняет старое.
- Коалесценция: в очереди живёт только последнее состояние, промежуточные
  вытесняются.

**Замерить и записать:** RTT, джиттер, долю потерь, устойчивую частоту
кадров, деградацию при загруженном Wi-Fi рядом. Это входные данные для
решения по частоте отчётов в M5.

**Готово когда:** цифры получены; надёжный канал переживает искусственную
потерю 20% кадров.

Чем проверяется потеря — записано здесь, потому что дважды подряд этот
критерий закрывался не тем тестом: **на модели линка с потерями в обе
стороны, с настоящей приёмной половиной (не её копией в тесте), включая
перезапуск любой из сторон посреди обмена.** Ни одного брошенного кадра,
ни одной перестановки.

**Про повторную выдачу — с оговоркой, и она осознанная.** Пока обе стороны
живы, наверх не уходит ни одного повтора. Но если перезапустится
**приёмник**, отправитель об этом не узнает: он сохранит эпоху и номер, и
первый же ретрай уже доставленного кадра попадёт в чистое состояние как
начало новой сессии. То есть доставка — «не реже одного раза», а не «ровно
один». Это принятая цена: приёмник перезапускается вместе со всей платой,
значит и приложение над ним начинает с нуля, дублировать там нечего. Чинить
это пришлось бы встречной эпохой приёмника в подтверждении — сложность ради
случая, в котором наверху и так ничего не осталось.

## M4 — клонирование личности

**Ветка:** обе + common/identity.

- TX сериализует снятое в M1: дескрипторы, строки, HID report descriptor,
  блоб метаданных GIP, содержимое Hello.
- Передача надёжным каналом, кэш в NVS на стороне RX, инвалидация при смене
  руля.
- RX поднимает USB **с этими** дескрипторами, а не с зашитыми.

Смысл не в удобстве: консоль кэширует метаданные по `VID/PID/Revision`, а
Device ID генерится из PUID крипточипа. Написанная от руки метадата рискует
разойтись с тем, за что ручается security-обмен.

**Готово когда:** хост видит устройство с VID/PID и строками настоящего
руля, а прошивка RX не содержит ни одного зашитого дескриптора G920.

## M5 — ПК-ветка end-to-end

**Ветка:** обе. **Зависит от:** M3, M4.

Первый работающий результат — специально раньше Xbox, потому что здесь нет
аутентификации, то есть нет самого рискованного звена, а тайминги самые
жёсткие и обкатать их лучше в отсутствие остальных переменных.

- TX держит руль в `c262`, читает HID-отчёты, пишет HID++ в OUT.
- RX — HID-устройство с клонированным report descriptor, туннелирует
  отчёты и HID++ вербатим.
- **Отдельный такт выдачи на RX:** отчёты хосту по своему таймеру из
  последнего полученного состояния, чтобы джиттер радио не протекал в USB.
- Коалесценция FFB, целевая частота **250 Гц — результат M3 получен**
  (контрольный замер 02.08.2026: 250 Гц идут 1250/1250 без потерь, пять
  ступеней подряд, при живой помехе рядом). 500 Гц закрыты не эфиром, а
  очередью отправки — драйвер отказывается принимать ~20% кадров; если
  когда-нибудь понадобится больше 250, чинить надо очередь ESP-NOW, а не
  радио. Разбор — в [`LATENCY.md`](LATENCY.md).

**Готово когда:** руль работает на Linux и Windows штатными драйверами
(`hid-logitech-hidpp` / G HUB), FFB ощущается, в игре нет заметных рывков.

**Риск:** HID в PC-режиме обычно на 1 мс, ESP-NOW — 1–2 мс в одну сторону.
Запас минимальный. Если ощущение FFB просядет — снижать частоту отчётов
осей нельзя, снижать частоту FFB можно.

## M6 — детектор хоста

**Ветка:** RX. **Зависит от:** M2 (признаки энумерации), M4 (личность —
без неё хост не заговорит и `T_silence` не измерить), M5 (есть куда
переключаться, и там же снимается `T_hid_idle`).

- Стартовая личность — GIP; уход в HID только по положительному признаку.
- Решающее дерево: тишина > **`T_silence`** → ПК; ответ + `0x06` → Xbox;
  ответ без `0x06` за 1 с → ПК.

**Пороги и откуда они берутся** (имена разведены с таймингами энумерации
M2 — раньше и те и другие звались T1/T2, и это спутало две вехи):

| Порог | Что означает | Откуда берётся |
|---|---|---|
| `T_silence` | тишина на уровне GIP: нет ответа на Hello | **после M4** — нужен годный Announce, чтобы хост заговорил. Брифинг берёт 2 с из спеки, M2 подтвердить не смогла |
| `T_hid_idle` | нет опроса IN в HID-режиме → откат в GIP | **M5** — там RX впервые встаёт HID-устройством |
| признаки энумерации | `device_qualifier`, `0xEE`, Extended Properties, рисунок проходов | **M2, сняты** — [`HOSTS.md`](HOSTS.md) |

⚠ **Дерево решений не достраивается до M4.** Признаки энумерации отделяют
macOS и Linux от Windows-подобных, но **Windows и Xbox по энумерации
категориально неразличимы** (общий стек USB), а разделяющий их `0x06`
приходит только после Announce.
- Вспомогательные признаки для досрочного вердикта: `device_qualifier`,
  строка `0xEE`, Extended Properties, фингерпринт энумерации.
- **Самокоррекция:** в HID-режиме нет опроса IN endpoint дольше T2 → откат
  в GIP. `0x06` в любой момент → GIP и фиксация.
- Кэш вердикта в NVS, детект привязан к появлению VBUS, а не к bus reset.

**Готово когда:** на каждой платформе из M2 вердикт верный, включая
холодный старт с выключенного хоста и повторное подключение к Windows.

## M7 — Xbox: GIP без аутентификации

**Ветка:** RX. **Зависит от:** M4.

- Полный конечный автомат GIP-устройства: Arrival → Idle → Active, Hello,
  ретрансляция метаданных, `Set Device State`, реакция на RESET/OFF/QUIESCE.
- Protocol Control: ACK, флаг ACME, сборка и разборка фрагментов.
- Status (`0x03`) — **локально на RX**: раз в секунду первые 10 с, дальше
  раз в 20 с. Через радио гонять незачем.
- Отчёты `0x20` / `0x21` — из туннеля.

**Готово когда:** Xbox распознаёт устройство как руль. До отвала по
неудачной аутентификации есть ~8 минут — этого хватает на отладку.

## M8 — auth passthrough

**Ветка:** обе. **Зависит от:** M7. **Самое рискованное — идёт поздно.**

- Ретрансляция сообщений `0x06` **вербатим**, в обе стороны, со сборкой
  фрагментов и корректными Protocol Control ACK.
- Приоритет `AUTH` над `INPUT` в очереди линка.
- Ориентир по реализации — `XBOneAuthUSBListener.cpp` из GP2040-CE.

Бюджет времени комфортный: ACK timeout хоста 100 мс, ACME каждые 60 мс,
reliable message timeout 1000 мс. GP2040-CE проходит аутентификацию с
троттлингом 15 мс на сообщение. ESP-NOW с 1–2 мс укладывается кратно.

**Готово когда:** консоль принимает руль как легальный аксессуар, устройство
живёт дольше 8 минут и переживает перезагрузку консоли.

## M9 — FFB на Xbox

**Ветка:** обе. **Зависит от:** M8.

- Туннелирование `0x0B` (Application Memory), `0x0C` (Equation States),
  `0x0D` (Set Equation) в сторону руля.
- Запросы `0x0A` (Initial Reports, Angle Change, Power Level, Vibration).
- Фрагментация для `0x0D` **не используется** — приёмный буфер устройства
  не должен превышать 64 байта, длинные уравнения идут несколькими
  запросами со смещением.
- Опционально: дизассемблер байткода уравнений для отладки — спека
  `H001443` полная, включая разобранный пример на 66 байт.

**Готово когда:** в гоночной игре на Xbox чувствуется обратная связь.

## M10 — надёжность и безопасность

**Ветка:** обе.

### Мёртвая рука (обязательно, вопрос безопасности)

Если радиоканал пропал, пока на руле стоят силы, **руль останется с
приложенным усилием**. Это не абстрактный риск: G920 стартует с тяжёлой
пружиной, а под уравнениями может держать значительный момент.

TX обязан вести таймер: нет кадров от RX дольше N мс → немедленно снять
силы:

- в Xbox-режиме — Loop State `0x02` (Forces Off), затем при затяжной потере
  `Set Device State: QUIESCE` (по спеке очищает состояние FFB, уравнения и
  память, возвращает Return-to-Center);
- в PC-режиме — остановить эффекты HID++, снять автоцентр.

То же в обратную сторону: RX при потере линка сообщает хосту «педали/руль в
нейтрали», а не морозит последний кадр.

### Остальное

- Переподключение руля на ходу, переподключение донгла, потеря и
  восстановление радиолинка без перезагрузки.
- Watchdog на обеих сторонах, журнал причин перезапуска.
- Индикация: состояние линка, вердикт хоста, ошибка — светодиодом.
- Аварийный оверрайд режима долгим удержанием кнопки.
- Пиринг: сброс, повторное сопряжение. **Сюда же возвращается забвение
  пира** (`forget_peer`: удалить из таблицы радио, отпустить состояние,
  стереть запись в NVS). В M3 такая функция была написана заранее — и
  простояла веху без единого вызывающего, за что веха и получила шестой
  BLOCK: она выглядела работающим механизмом, а исполнение по ней не шло.
  Удалена; писать её нужно вместе с кнопкой, которая её зовёт, и не раньше.

## Сводка по срокам и зависимостям

| Веха | Ветка | Блокируется | Даёт |
|---|---|---|---|
| M0 | обе | — | сборка, логи |
| M1 | TX | M0 | весь снифф руля, закрытие 6 неизвестных |
| M2 | RX | M0 | эталоны хостов, T1/T2 |
| M3 | common | M0 | цифры по радио |
| M4 | обе | M1, M3 | RX выглядит как настоящий руль |
| M5 | обе | M4 | **работающий продукт для ПК** |
| M6 | RX | M2, M5 | автоопределение платформы |
| M7 | RX | M4 | Xbox видит руль |
| M8 | обе | M7 | **работающий продукт для Xbox** |
| M9 | обе | M8 | FFB на Xbox |
| M10 | обе | M5 | безопасность и живучесть |

Две точки, где есть что показать: **M5** — руль работает по радио на ПК;
**M8** — консоль приняла руль. До M5 всё промежуточное.

## Что нужно из железа и когда

| Когда | Что |
|---|---|
| M0 | 2× ESP32-S3-DevKitC-1 |
| M1 | G920 + БП, USB-разъёмы для врезки в линию руля |
| M2 | Xbox, ПК с Windows, ПК с Linux |
| M5 | гоночная игра на ПК |
| M9 | гоночная игра на Xbox |
| M10 | ничего нового |

Raspberry Pi с `usb-proxy` в списке нет намеренно: M1 закрывает сниффинг
силами самого передатчика. Пи остаётся резервом на случай, если USB Host
на S3 окажется слишком капризным для снятия чистого лога.
